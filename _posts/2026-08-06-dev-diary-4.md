之前自己搭的基础框架（单例、对象池）解决的是"工具"问题，但项目继续往下做，代码该怎么组织、数据怎么流动、UI 怎么刷新，这些"架构"问题光靠工具解决不了。评估之后引入了 QFramework——一个纯 C# 的分层架构框架，核心思想一句话：**Model 存数据，System 写逻辑，Command/Query 管理读写，Controller 连接 Unity**。

框架只用一个 `QFramework.cs` 文件就能跑，把 `Assets/QFramework` 整个文件夹拷进工程即可，零配置。

## 分层架构总览

QFramework 把一个游戏模块分成几个明确职责的层：

```
Unity 世界          ←→        框架世界

MonoBehaviour                  ┌──────────┐
(Controller) ──发命令/查询──→  │Architecture│ ← 模块总管
     ↑ 刷新 UI                 └─┬──┬──┬──┘
     │         ┌────────────────┘  │  └───────┐
     │         ▼                   ▼          ▼
     │    ┌─────────┐       ┌──────────┐ ┌────────┐
     └────│  Model  │◄──────│  System  │ │Utility │
  自动通知 │ (数据)  │ 读写  │  (逻辑)  │ │(工具)  │
          └─────────┘       └──────────┘ └────────┘
               ▲ Write(Command) / Read(Query)

  事件系统(TypeEventSystem)贯穿全局，模块间广播通信
```

每一层只干自己该干的事，这是整个框架最重要的约束。

## Architecture — 模块总管

每个游戏模块（背包、商店、关卡……）对应一个 Architecture，可以理解为仓库总管：持有这个模块所有的 Model、System、Utility，是个单例，全局只有一份。

```csharp
using QFramework;

namespace CounterApp
{
    public class CounterApp : Architecture<CounterApp>
    {
        protected override void Init()
        {
            RegisterModel(new CounterModel());
            RegisterSystem(new AchievementSystem());
            RegisterUtility(new LoggerUtil());
        }
    }
}
```

之后在任何地方，一行代码拿到模块入口：

```csharp
IArchitecture architecture = CounterApp.Interface; // 第一次访问时自动初始化
```

架构类本身很薄，只做注册，逻辑都放在 System 里。

## Model — 只存数据

Model 的规则只有一条：**只负责存数据，不写业务逻辑，也不碰 UI**。

它最核心的能力是 `BindableProperty<T>`（可绑定属性）——值一变，所有订阅者立刻收到通知。UI 自动刷新全靠它：

```csharp
public class CounterModel : AbstractModel
{
    public BindableProperty<int> Count { get; } = new BindableProperty<int>(0);

    protected override void OnInit()
    {
        // 可选：从存档读数据
        // Count.Value = PlayerPrefs.GetInt("Count", 0);
    }
}
```

改数据和监听数据：

```csharp
// 写数据
var model = CounterApp.Interface.GetModel<CounterModel>();
model.Count.Value = 10; // 值变了，UI 自动收到通知

// 读数据（UI 侧订阅，注册时立刻收到一次当前值）
model.Count.RegisterWithInitValue(count =>
{
    Debug.Log($"当前数值：{count}");
});
```

对比一下以前的做法：以前改完值要手动找 UI 更新，UI 代码和逻辑代码互相耦合；现在双方只知道"这个属性"，值一变 UI 自己刷新。

## System — 业务逻辑容器

Model 不写逻辑，业务逻辑全部放 System。它读 Model、写 Model、发事件，但绝不碰 UI。打个比方：Model 是钱包（只装钱），System 是会计（管怎么算钱）。

```csharp
public class AchievementSystem : AbstractSystem
{
    protected override void OnInit()
    {
        var counterModel = this.GetModel<CounterModel>();

        counterModel.Count.Register(count =>
        {
            if (count >= 10)
            {
                Debug.Log("成就解锁：身家过十！");
            }
        });
    }
}
```

注意 `this.GetModel<CounterModel>()` 不用 new，不用传引用，框架自动注入。System 里可以写任何逻辑，但绝不能写 `GetComponent` 或 `GameObject.Find`——那些是 Controller 的事。

## Command / Query — 读写封装

直接在 Controller 里写 `model.Count.Value++` 也能加金币，但以后金币+1 还要记录日志、检查成就、更新排行榜时，代码会散得到处都是。

Command 把"一个动作"封装成一个独立的类：

```csharp
public class AddCountCommand : AbstractCommand
{
    public int Amount { get; set; } = 1;

    protected override void OnExecute()
    {
        var model = this.GetModel<CounterModel>();
        int oldValue = model.Count.Value;

        model.Count.Value += Amount;

        // 发事件，通知所有订阅者
        this.SendEvent(new CounterChangeEvent
        {
            OldValue = oldValue,
            NewValue = model.Count.Value
        });
    }
}
```

发送命令有两种方式，效果一样：

```csharp
this.SendCommand(new AddCountCommand { Amount = 5 });
this.SendCommand<AddCountCommand>(); // 无参命令用泛型，框架自动 new
```

需要返回值时用 `AbstractCommand<TResult>`。Query 则是"读"的封装，把"怎么算"藏起来，读的人不用关心数据从哪来、怎么算。简单场景下优势不明显，但如果金币数是"现金 + 银行存款"算出来的，Query 的价值就体现了。

## 事件系统 — 跨模块通信

`Count.Register(...)` 只能监听单个属性，属于 Model 级别通知。"玩家死亡"、"关卡通关"这类全局事件，要用事件系统。

QFramework 按"类型"区分事件，不需要字符串 key：

```csharp
// 定义事件（普通 struct 就行）
public struct PlayerDiedEvent { }

// 发送
TypeEventSystem.Global.Send(new PlayerDiedEvent());

// 订阅
TypeEventSystem.Global.Register<PlayerDiedEvent>(e =>
{
    Debug.Log("玩家死了，显示复活界面");
});
```

**最大的坑在这里：注册事件后必须注销**，否则对象销毁后订阅还在，会造成内存泄漏和幽灵回调。正确写法是注册后立刻挂上自动注销：

```csharp
this.RegisterEvent<CounterChangeEvent>(OnCounterChanged)
    .UnRegisterWhenGameObjectDestroyed(this); // 对象销毁自动注销
```

规则：`RegisterEvent` 后必须跟一个 `.UnRegisterWhenXxx(...)`。

## Controller — 连接 Unity 的桥

Model、System、Command 都是纯 C# 类，不继承 MonoBehaviour。但 UI 按钮、文本、碰撞器必须挂 MonoBehaviour，Controller 就是中间的翻译官。

脚本实现 `IController` 接口，提供一个 `GetArchitecture()` 方法，就自动获得发命令、读模型、订阅事件的全部能力：

```csharp
public class CounterViewController : MonoBehaviour, IController
{
    [SerializeField] private Text countText;
    [SerializeField] private Button addButton;

    public IArchitecture GetArchitecture() => CounterApp.Interface;

    private void Start()
    {
        // 订阅数据，自动刷新 UI（注册时立刻刷新一次）
        this.GetModel<CounterModel>()
            .Count
            .RegisterWithInitValue(count =>
            {
                countText.text = $"金币：{count}";
            })
            .UnRegisterWhenGameObjectDestroyed(gameObject);

        // 按钮只发命令，不直接改数据
        addButton.onClick.AddListener(() =>
        {
            this.SendCommand(new AddCountCommand { Amount = 1 });
        });
    }
}
```

## 完整数据流

玩家点击按钮，金币 +1，UI 刷新，成就系统检查成就：

```
玩家点击按钮
    │
    ▼
CounterViewController (IController)          ← MonoBehaviour，接收 Unity 输入
    │  this.SendCommand(new AddCountCommand())
    ▼
AddCountCommand.OnExecute()                  ← 命令：改数据 + 发事件
    │  model.Count.Value += 1
    ▼
CounterModel.Count (BindableProperty<int>)   ← 数据变化，自动触发通知
    │        │
    │        ├──────────────────────────┐
    ▼                                  ▼
Controller 订阅的回调                    AchievementSystem 订阅的回调
countText.text = "金币：1"              if (count >= 10) 解锁成就
```

两点关键：数据只在一个地方被修改（Command 里），UI 和成就系统都是被动收到通知；Controller 不碰逻辑，Command 不碰 UI。

## 工具包：AudioKit / UIKit / ResKit

核心框架之外，`Toolkits` 里还有三个可选工具包，和核心框架解耦，可以单独用：

| 工具包 | 解决的问题 | 对应旧做法 |
|---|---|---|
| AudioKit | 音频播放管理 | 到处挂 AudioSource、手动找 Clip |
| UIKit | UI 面板管理 | 手动 SetActive 切面板 |
| ResKit | 资源加载管理 | Resources.Load / 直接引用 |

AudioKit 一行代码播音乐（`AudioKit.PlayMusic("HomeBg")`），音量开关本身就是用 `BindableProperty` 写的，源码可以作为学习范例。UIKit 把每个面板抽象成 UIPanel 类，`OpenPanel<T>()` / `ClosePanel<T>()` 自动管理生命周期。ResKit 用 AssetBundle + 引用计数解决热更新和资源释放问题，正式项目必用，学习项目先用 `Resources.Load` 就够。

## 各层职责速查

| 层 | 可以做什么 | 绝不能做什么 |
|---|---|---|
| Model | 存数据（BindableProperty）、OnInit 读存档 | 写 if-else 业务逻辑、碰 UI |
| System | 业务逻辑、订阅事件、读写 Model | 碰 UI（GetComponent 等） |
| Command | 改数据的写操作、发事件 | 碰 UI |
| Query | 读数据的封装 | 改数据 |
| Controller | 接收输入、刷新 UI、发命令/查询 | 直接改数据、写业务逻辑 |
| Utility | 通用工具（日志、加密等） | 存状态、写业务 |

五条约束：

1. 写数据走 Command，读数据走 Query
2. 注册事件必注销
3. Model 只存数据，看到 if-else 就搬去 System/Command
4. Controller 是唯一碰 Unity 组件的地方
5. 一个 Scene 对应一个 Architecture，场景切换时调用 `Deinit()` 清理
